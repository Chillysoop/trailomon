Optional tools to build next

F1Let the game capture its own test screens

Extend the existing test scenes to open a requested state, perform its scripted actions, save a rendered screenshot and exit. Inspect those images directly. First prove this on Options and combat setup, then expand as features need it. Prefer a test-only native capture extension; an HTML5 test build is a fallback, not a new shipping platform.

Evidence: the existing 36 GUI states already remove navigation. A Defold screenshot extension exposes post-render PNG capture. Its compatibility with our pinned Windows engine still needs a small proof.

Cost: one bounded proof and integration PR, with a new test-only dependency. Recommend YES, first: largest remaining saving for visible changes. It does not replace Windows focus/input or listening checks.

F2Give native tests a stable launcher

Reuse one owned test executable location when its engine hash is unchanged. Refresh only its game data, keep player saves isolated, and retain timestamped reports. Guard against a running executable or an engine-version mismatch.

Evidence: timestamped test executable paths caused repeated Windows firewall interruptions. Reusing the already-checked path worked in the last batch. This cannot guarantee Windows will never prompt; it does not change firewall settings.

Cost: one small script PR plus lifecycle checks. Recommend YES: remove the repeated manual workaround.

F3Record exactly which evidence can be reused

Write a local verification record with the test command, duration, outcome and hashes of its relevant code, test, engine and render inputs. An explicit check can say why earlier evidence still applies or which changes require a rerun. Keep full CI for changed game code.

Evidence: the final ZIP already matched all five playtested executable/data files byte for byte. That let us reuse visible-game evidence after documentation changes. A small record makes that reasoning repeatable.

Cost: one small tooling PR; careful dependency lists, conservative fallback for unknown inputs. Recommend YES, after F1/F2: avoid repeated expensive visual checks. Do not spend time caching tests that already take milliseconds.
